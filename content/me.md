## 经历

### 高中：把网课塞进 MP3

高中住校，管得很严，两周只放半天假，不让带电子设备。真正的问题不是找不到学习资源，而是没有时间学。

高二时我发现，网课也能像我平时听的课程音频一样下载下来。于是回家时把网课视频转成音频，存进一个很小的 MP3，带回学校配着打印的讲义听，听不懂就倒回去再听。先从物理开始，跑通以后又扩展到数学、语文和化学。这种学法短期见效很慢，阶段考试也不按我的进度出题，但我没有怀疑过这条路线，一直走到了高考。

我的 B 站简介到现在还写着「哔哩哔哩高级中学毕业生」。

### 2023：从单片机开始写代码

高考后的暑假有了第一台自己的电脑，跟着 B 站教程学 C 语言和 51 单片机，后来玩过 ESP32、STM32，又学了 C++ 和 Qt。

兴趣经常换：试过觉得没那么好玩，就放下去做别的。但放下一个方向，不等于之前学到的东西都白费。现在不做嵌入式了，看到「ESP32 接个 LLM API 就叫 AI 硬件」时，还是能一眼看懂它在做什么。

### 2023—2025：转专业、自学和 C#

入学时读水利水电，大一下转到计算机学院，被调剂到人工智能专业。比起学校的课，我更习惯自己挑学习资源：B 站网课、[CS 自学指南](https://csdiy.wiki/)、MIT 的 The Missing Semester，然后自己做项目。

大二下的《软件构造基础》是我印象最深的一门课，第一次从零做出一个真正的软件项目（[DAW](https://github.com/shenxianovo/DAW)）。为了这门课提前学了 C#，结果一直用到现在：Unity、UWP、WinUI，再到用 ASP.NET 写后端。

大一时用 Azure 学生额度租了第一台服务器，后来慢慢扩展成三台低配 Linux 服务器上的十余个服务，用 Docker Compose 部署，GitHub Actions 发布，Prometheus、Grafana 和 Uptime Kuma 监控告警，还自己写了认证服务。

### AI 编程方式的变化

- **2024 春**：在浏览器和编辑器之间来回复制代码。
- **2025 春**：VS Code 里用 GitHub Copilot，DAW 就是这样写的。
- **2026 春**：转向 Claude Code、Codex 这类能自己探索代码库、改文件、跑验证的 Agent。

印象最深的一次：DAW 的波形和频谱图渲染，2025 年我借助 Gemini 2.5 Pro 也没做好，仓库里还留着一条「[Gave up implementing spectrogram. QAQ](https://github.com/shenxianovo/DAW/commit/304aee939e7269a0e4739bc6b2cabe8f102894ad)」。后来 Opus 4.6 出来，几句话就解决了。这比任何评测分数都更让我感受到模型的进步。

### 2024—2026：动漫协会，从部长到社长

2024—2025 学年当武汉大学动漫协会演音部部长，2025—2026 学年当社长。原因并不宏大：因为没人做。

刚接手时几乎没有交接材料，于是我写了演音部工作手册。当社长后建了 GitHub 组织 [WHUDAYS](https://github.com/WHUDAYS) 和管理层文档仓库，按学年和部门归档资料、写交接材料，希望经验不再只留在某一届负责人的脑子里。

做下来也发现，留下流程和文档，不等于建立了好的协作机制。负责人和成员怎样讨论、决定、共同承担，比把文档写全复杂得多。漫协终究是兴趣社团，办活动、写文档都应该服务于其中的人，而不是变成负担。

### 2026—现在：Orisumi

[Orisumi](https://github.com/shenxianovo/Orisumi)（原名 Heartbeat）一开始只想记录「我今天在电脑上干了什么」，后来目标变成了保存一个人经历了什么：设备、应用和 AI 助手都会换，但经历过去就没法再采集。它已经推倒重写过两次，从围绕设备活动的数据结构，转向更通用的实体、观测者和观测。[文档站](https://docs.orisumi.dev)

我做它，很大一部分原因是想让 AI 更懂我。未来的模型会强很多，但它不会天然知道我经历过什么、在意什么。与其等模型「自动认识我」，不如从现在开始自己积累。这份文档也是同一计划的一部分。

当然，直接动力还是好玩，想做点东西。

## 我在意的事

- **把短暂的经验变成长期的积累。** 不希望组织每次换人就把前人的经验丢光。
- **先理解问题本质，再决定要不要增加复杂度。** 一个功能老是需要补丁时，更愿意回头检查模型或架构。
- **让软件和 AI 的协作方式发生更深的变化。** 不只是往软件里加一个聊天框，而是让代码、文档、业务术语、架构决策和自动化验证构成共享上下文，让 Agent 真正参与系统的建设和维护。

> Stop putting AI into software.
> Grow software out of AI.

## 我怎样表达

我常常能很快认出一个东西「不对」或「不喜欢」，却很难凭空说清原因：技术架构、UI、音乐都是这样。识别容易，描述困难，像一个正向好算、逆向难解的函数。给我具体案例来比较、选择，比让我凭空描述标准容易得多。

比起当面说，我更习惯打字，因为文字可以反复修改。但不管哪种，都会有「知道想表达什么，却不知道怎么说」的时候。

## 我希望怎样与 Agent 合作

- 不用称呼我，直接说事。
- 先理解真实目标、约束和上下文，再动手，不急着打局部补丁。已有的代码、文档和约定，先弄清它为什么存在。
- 有多种方案时，选简洁、可靠、可解释、可维护的那个。
- 发现 Bug 时，先想测试为什么漏掉；能复现就先做最小复现，再修根因，回归验证与改动范围相称。
- 区分事实、猜测和建议，坦诚说出不确定的地方。
- 觉得我的判断有问题时，说清问题在哪、为什么、还有哪些选择，和我讨论；不要只给结论，也不要一味附和。
- 我说不清原因时，用具体案例、对照或候选描述帮我说清，不要替我认定原因。
- 帮我写东西时，看用途决定要不要保留我的语气。
- 提醒和建议可以主动给；替我做决定、改计划、直接干预，需要我事先授权。
